Start

What KodaHosting is

KodaHosting turns a phone into a real Minecraft server. Not a client and not a remote control for somebody else's machine: the server process runs on the device, the world files sit in the device storage, and the app is the control panel around it. That one decision explains almost every design choice in this codebase, including the odd ones.

Three planes do the work, and it helps to keep them apart in your head.

  • The device plane is the app itself. It downloads server jars and Java runtimes, starts and stops the process, owns the console, browses and edits files, makes backups and applies every change. If something mutates a server, it happens here.
  • The connectivity plane is the tunnel. A bundled reverse proxy client forwards the Minecraft ports and the web dashboard through a public server, so friends can join without your home address ever leaving the router.
  • The control plane is Supabase. It knows which devices belong to which user, which servers exist, which ports are taken, which releases are published and which extensions are approved. Every write goes through a function that checks a per device token.

A fourth piece is easy to miss: KodaDash, a Java plugin that runs inside the Minecraft server and serves a web dashboard on port 7867. The app writes small JSON files into the server folder for stats, backups and schedules, and KodaDash picks them up, which is why the dashboard still shows sensible numbers while the phone sleeps.

Your own instance

The public repository is a complete snapshot of the source. What it cannot contain is the instance: the addresses, keys and accounts that belong to whoever runs it, plus the admin tooling that holds the service role key. Here is where the line is drawn.

Missing on purposeWhy it matters
secrets_local.hthe Supabase URL, the public key, the AI key and the tunnel host that get compiled into the app
The Supabase projectits rows, storage objects, auth users and the edge function secrets
Tunnel and DNS credentialsthe reverse proxy token and the DNS provider keys for custom domains
Signing materialthe release keystore, its passwords and the Play credentials
The admin toolsthe web panel and the Kotlin admin app

One exception is on purpose. The imprint and the privacy policy name a real operator with a real address, because German law requires it, and a service that hides who runs it is not trustworthy anyway.

Running your own

  1. Clone the repository and build it once with JDK 21.
  2. Create a Supabase project and apply the SQL files from supabase/ in order, migrations first, then security fixes, then releases and extensions. Each file ends with a statement that reloads the API schema.
  3. Create the storage buckets your features need: artifacts, release_images, support_attachments, extension_artifacts, extension_icons.
  4. Deploy the edge functions and give them their secrets. get-tunnel-config is the one you cannot skip, the app asks it for its tunnel credentials.
  5. Run an frps server, or use an existing service, and put its address plus your Supabase URL and public key into the native header file.
  6. Build a signed release and install it. The first screen registers a device and creates the row everything else hangs off.
  7. Optional: the Discord bot with your own token, and the admin panel if you prefer a browser over the admin app.
A fresh instance starts empty on purpose. Without a backend the app still runs, but the first start cannot register a device and most screens stay quiet.

Building the app

One Gradle module plus a small native part that boots the embedded JVM. The first build takes a few minutes, later ones are quick.

export JAVA_HOME=/path/to/jdk-21        # newer JDKs break the Gradle version in use
./gradlew :app:assembleDebug            # debug apk
./gradlew :app:assembleRelease -PKEYSTORE_PW=... -PKEY_PW=...
adb install -r app/build/outputs/apk/release/app-release.apk
./gradlew :app:testDebugUnitTest        # unit tests, finishes in seconds

The first trap: a debug build and a release build cannot replace each other, because their signatures differ. Decide early which one your test device carries, otherwise you will uninstall the app and lose its data on the way.

The second trap: release builds strip every log call. Logcat stays silent in a release build, for your code and for the framework wrappers alike, so show diagnostics in the interface instead of trusting a log line. The app has its own debug log screen for exactly this reason.

Relevant devices are arm64 and run Android 11 or newer. The APK bundles only arm64 libraries, so an x86 emulator will install nothing useful.

Your servers, the home screen

The home screen lists every server as a card with its name, type, version and live state. A tap opens the server screen, a long press gives the quick actions that matter in the moment, and the cards carry the numbers you check most often: players, memory and uptime.

Servers that are hibernated appear greyed out with a wake button. Servers that are starting or stopping show the animated state instead of a button, so you can see that something is happening without opening the console.

Above the list you find the entry points to settings, support, Discord and the debug log, plus the button that starts a new server. The stats card at the top summarises how many servers exist, how many are online and how much memory they use together.

The app

Creating a server

The wizard is deliberately linear, because every step has consequences that are hard to undo later. Name and join address first, then the server software, then the Minecraft version, then memory, then the world.

  • Server type: Paper, Purpur, Folia and Vanilla for plugins, Fabric, Forge and NeoForge for mods, and PumpkinMC, the native server that needs no Java at all.
  • Minecraft version: only versions the chosen software actually publishes, with short notes on mod and plugin availability.
  • Memory: the wizard shows what the device can spare while other servers keep running.
  • World: type, seed and a few presets, including a flat world for building tests.
  • Setup mode: the Koda design installs a tuned configuration with sensible gameplay defaults, or you start from a clean vanilla setup.

After the wizard the server is created locally and registered in the cloud, and the first start downloads the server jar and, if needed, the matching Java runtime. Both downloads show progress in the console.

The app

The server dashboard tab

The dashboard is the tab you land on, and it is built to answer three questions: is the server healthy, who is playing, and what can I do right now.

Status and address come first, with the join address in a copyable form and a button to change it. The player panel lists who is online, with avatars and one tap into the full player sheet for stats, inventory and moderation actions. Memory and CPU usage update live, and the quick action row starts, stops and restarts the server with a confirmation countdown when players are online.

When a server crashes, the dashboard is also where the crash report appears: a classified reason, the suggested fix, and the last log lines. Applying a suggested fix is a single tap and never guesses, it changes one known setting and tells you what it changed.

← Creating a serverThe console →
The app

The console

The console streams the server output live, stripped of the colour codes that Minecraft servers write, with the levels highlighted so warnings and errors stand out. Auto scroll follows the newest line until you scroll up, then it stays where you are, which is the behaviour you want while reading a stack trace.

Above the input field sits a row of quick commands, and extensions can add their own chips to it. Commands you type are sent to the server process directly, so anything the server understands works here, including plugin commands.

  • Copy puts the visible log on the clipboard, handy for a support ticket.
  • Log opens the full verbose log of the app itself, useful when a download or a start fails.
  • AI crash analysis offers to read a crash with you, and asks for consent before anything leaves the device.

The app

Files: browse, edit, unpack, export

The file tab is a full manager for the server folder. Tap a folder to enter it, tap a file to open the editor, long press an entry for the action sheet with rename, copy, cut, delete and share.

  • Import brings files in from anywhere the phone can read, including other apps and cloud providers.
  • Unpack here extracts ZIP and RAR archives in place. Password protected RAR files are reported instead of failing silently.
  • Export writes the whole folder as a ZIP into Downloads, without a wrapper folder so it can be reimported directly.
  • NBT viewer opens player data, level data and other binary NBT files as a readable tree, read only by design.

The editor is for text files up to a megabyte, with syntax friendly handling for properties, JSON and YAML, and a save button that warns when the server is running because some files are only read at start.

← The consoleMods and plugins →
The app

Mods and plugins

Mods and plugins are managed in their own tab, and the install side is a Modrinth browser: search, filter by the server type and version, install with one tap, update with one tap.

The installed list shows every jar with its metadata read from the file itself: name, version, authors and icon, with a Modrinth lookup as a fallback because many server jars ship no image. A switch enables and disables a jar by renaming it, and the trash keeps removed files for a while instead of deleting them outright.

Server jars are not app extensions. This tab manages software that runs inside Minecraft. App extensions are a different system, described further down.

Server management

Starting, stopping, restarting

Starting a server is one tap, and the app orchestrates a lot behind that tap: it checks memory and network budget, prepares the runtime, writes generated configs, starts the process, and waits for the startup line before reporting the server as online.

Stopping asks the server politely first, sends the save command, and only kills the process when it does not react. The force kill option exists and warns that world data may be lost, which is why it sits behind a confirmation.

Restarts reuse the stop path, so players do not lose progress. When people are online, the server announces the restart in chat with a countdown.

← Mods and pluginsChanging the Minecraft version →
Server management

Changing the Minecraft version

Version changes live behind a wheel on the dashboard and are treated as a structural operation, not a setting. The list only shows versions the current server software really publishes, and the switch takes a backup first.

  • Upgrades ask for a backup but let you continue without one.
  • Downgrades require one, because worlds and chunks are not backwards compatible.
  • The old jar is kept until the new one started successfully.

Plugins and mods are not migrated automatically. After a version change the app tells you to check the mods tab, and Modrinth update checks usually find matching builds.

← Starting, stopping, restartingBackups and restore →
Server management

Backups and restore

Backups are ZIP archives of the whole server folder, stored beside the app, and they are the reason a bad afternoon stays an afternoon. You can create one manually, or let the app keep a schedule: on stop, daily, or both.

  • Keep count decides how many copies survive the rotation.
  • Restore replaces the server folder with the chosen state and keeps the current files until the restore finishes.
  • Size and age are shown per backup, so cleaning up is a decision and not a guess.
Restoring needs a stopped server. The app refuses otherwise, and that refusal has saved more worlds than any warning text could.

Server management

Automations and schedules

The automation sheet plans recurring work: restart, stop, save the world, announce something or run a command. Jobs can run on an interval or daily at a fixed time, and they can wait until nobody is online.

A nightly restart with an announcement a few minutes ahead is the usual first job. The app notes in chat before an empty only restart, so players are never surprised, and the KodaDash dashboard shows the same job list because the app mirrors it into the server folder.

Server management

Players, stats and moderation

Player management covers both worlds: the live roster of who is connected, and the history of everyone who ever joined. Tapping a player opens a sheet with their skin, playtime, statistics and inventory rendered from the actual save data.

  • Live actions: kick, ban, pardon, op and deop, message, gamemode, teleport, experience.
  • Care actions: heal, feed, saturate, and a full inventory wipe that asks twice.
  • Inventory can be rearranged by dragging items between slots, which writes straight into the player save.
  • Whitelist switches per player and for the server as a whole, with the same rules the server uses.

Server management

The MOTD editor

The MOTD is the two line text players see in their server list, and the editor treats it like the formatting puzzle it is. Colours, bold, italic, underline, obfuscated, reset, plus hex colours in all three notations Minecraft accepts, are inserted as proper codes while you type.

Every code button inserts into the field and keeps your cursor in the right place, and a live preview shows how the text will look. If you prefer raw editing, the plain properties view is still one tab away.

The MOTD field can be resized by dragging its lower edge, which helps with long texts and small screens.
← Players, stats and moderationResource packs →
Server management

Resource packs

A resource pack is served by the server itself, and the app handles the whole chain: pick a ZIP, upload it into the server folder, set the pack URL and the SHA-1 checksum in the properties, and switch the pack requirement on or off.

KodaDash serves the file over the tunnel so players can download it through the join address, which means no external hosting is needed. The dashboard shows whether a pack is active and how large it is.

← The MOTD editorWorld settings: type, seed, gameplay →
Server management

World settings: type, seed, gameplay

World type, seed, gamemode, difficulty, view and simulation distance, spawn protection and hardcore mode are all edited in the settings tab and written into server.properties. The app reads the file back afterwards and compares it to what it wrote, so manual edits are never overwritten silently.

If you change a value by hand while the server is stopped, the app notices the drift on the next visit and asks which value should win. That is the reason the file and the interface never disagree, a problem that otherwise shows up as a server that ignores its own settings.

← Resource packsMemory settings →
Server management

Memory settings

Each server gets its own heap size, and the app guards the total: Android keeps a reserve for itself, and starting a second server can only use what is left. The RAM slider shows what fits right now and warns when a value would push the device into swapping.

Changing memory requires a restart to take effect, because it becomes a JVM start argument. The app uses it to power the crash advice as well: an out of memory crash arrives with a suggested value that fits the device, not an arbitrary number.

← World settings: type, seed, gameplayJava runtimes →
Server management

Java runtimes

Minecraft servers need a Java runtime per version, and the app bundles none of them by default. Instead it downloads the matching runtime when a server needs it, from JDK 25 down to 8 and 17, and remembers the choice per server.

  • Automatic picks the runtime that matches the server version and software.
  • Manual lets you pin a version, for example a mod that insists on Java 17.
  • Fallback starts the server anyway when a runtime is broken, and tells you what it did and why.

The download progress is visible in the console tab, and runtimes are shared between servers, so the second server of the same version starts much faster.

← Memory settingsHibernate and wake →
Server management

Hibernate and wake

Hibernation takes a server off the air without deleting it: the app stops the process, removes the join address from the network, packs the folder, and leaves a marker behind so the dashboard shows a sleeping server instead of a broken one.

Waking it restores the folder, requests a fresh join address, and starts the process. The point of the feature is the phone: a hibernated server uses no memory, no battery and no tunnel, which matters when you host more than one world.

The transfer between two devices speaks the same language, which is why both features share their packing code.
← Java runtimesMariaDB and Redis →
Server management

MariaDB and Redis

For plugins that need a database, the app can run MariaDB or Redis next to the server, on the phone, with credentials you choose in the wizard. Both run as native processes from the same runtime set that runs the servers, so there is nothing to install separately.

The connection details are shown in the database card, including port, user and a generated password, and the app keeps the data directory beside the server folder so a backup covers both. The server type Database in the main list is exactly this: a database instance without a Minecraft server around it.

← Hibernate and wakeTunnel and join addresses →
Connectivity

Tunnel and join addresses

Players cannot reach a phone on a home network directly, so the app runs a reverse proxy client that forwards the Minecraft ports and the dashboard through a public server. The address players use is the join address shown on the dashboard, and it changes with the tunnel, not with your home connection.

The tunnel credentials are not stored in the app package. The app asks the backend for them on demand, caches them for a few hours, and refreshes them in the background, which is why an expired tunnel heals itself after a while instead of needing a reinstall.

  • Join address is created automatically and can be changed once per day.
  • Both Java and Bedrock ports are forwarded when Bedrock support is on.
  • The dashboard travels through the same tunnel on its own port band.
← MariaDB and RedisCustom domains →
Connectivity

Custom domains

If you own a domain, the wizard links it to the server with an SRV record: it shows the exact record values, copies them to the clipboard, and verifies through public DNS until the record is live. No DNS knowledge is required, but the wizard explains what it does at each step.

Because DNS changes take time, the wizard can finish later: the server stays reachable on the standard address until the record resolves. The same card can unlink the domain and return to the default address.

← Tunnel and join addressesPorts and network →
Connectivity

Ports and network

Each server gets its own port, and the app manages both halves: the local port the server listens on, and the remote port the tunnel publishes. KodaDash runs on a separate port from a reserved band, so it never collides with a Minecraft server.

The port list on the dashboard shows what is in use and what is free. When a port is taken by another app on the phone, the server start fails with a clear message and a suggestion instead of a generic crash.

← Custom domainsNetwork budgets and the network alarm →
Connectivity

Network budgets and the network alarm

Hosting from a phone means hosting on a connection that other people also use. The app therefore tracks how much bandwidth each server consumes and can hold a server back when a rule is set.

  • Budget rules define a speed limit and a split between servers, so one busy world cannot starve the others.
  • The network alarm warns when the shared tunnel server is under pressure, before players notice lag.
  • Protection mode stops servers when the network is overloaded and tells you why, instead of letting everyone lag.

Connectivity

Bedrock crossplay

With Geyser and Floodgate installed, Bedrock players can join a Java server. The app installs both plugins, writes their configuration from templates that already match the server settings, and opens the extra port the Bedrock protocol needs.

PumpkinMC, the native server, has Bedrock support built in, so on that server the switch is simply part of the server itself. Either way the dashboard shows both addresses: the Java one and the Bedrock one with its port.

Voice chat

For Simple Voice Chat the app installs the plugin or mod matching the server type, opens the extra UDP port through the tunnel, and writes the voice chat configuration with the correct port and address. The result is voice that works for Java and Bedrock players without a separate server.

Account and support

Your account

An account is optional, and the app works fully without one. With an account you get your servers on the website, the ability to recover them on a new device, and the family features.

Signing in happens with email and password or with Google, and the account links to the device, not the other way around: the device token stays the credential that authorises every write, and it never leaves the phone.

← Voice chatLinking a Minecraft account →
Account and support

Linking a Minecraft account

Linking proves that a Minecraft player belongs to you, which is what the lobby and the /join command use. The app generates a short code, you join the lobby server and type /link with that code, and the link appears in your account card.

One Minecraft account belongs to one device at a time. Moving it to another device is a deliberate action, and the old device loses the link when the new one takes it, which keeps shared accounts from drifting apart.

← Your accountYour nickname →
Account and support

Your nickname

A nickname is what friends see in the shared server list and in the lobby, instead of a device identifier. The app asks once after the first start and then about once a day when you open a screen that shows other people, and it can be changed in the settings at any time.

← Linking a Minecraft accountMoving servers to a new device →
Account and support

Moving servers to a new device

Transfer takes a server from one phone to another over the local network, encrypted end to end. The old device packs and serves the files, the new device downloads and adopts them, and the join addresses follow the server.

  • Pairing works by picking the target device or by an eight character code, and the receiving side always confirms with a dialog that names the sender.
  • Encryption uses a key that only exists during the transfer window, so the LAN traffic is unreadable even on a shared network.
  • Cleanup happens after the receiving side confirms, never before, so an interrupted transfer leaves the old copy intact.
← Your nicknameFamily accounts and permissions →
Account and support

Family accounts and permissions

One account can hold several servers, and other people can be linked to them with individual permissions: who may start, stop, hibernate, delete, manage players, install plugins or use the console. The permission dialog lists them as switches, and a main account keeps full control.

Everyone signs in with their own credentials, so the permissions apply to people, not to devices. Revoking access is one switch and takes effect on the next action.

← Moving servers to a new deviceKodaCluster →
Account and support

KodaCluster

Two phones can be joined with a USB cable into a small fleet: one device is the master and shows a dashboard of both machines, and can start and stop servers on the other device. The link speaks a small JSON protocol over USB, so it works without a network at all.

The slave device has to be set to file transfer mode, and the USB accessory filter is part of the app manifest, so the cluster connects without any setup inside the app.
← Family accounts and permissionsTickets and bug reports →
Account and support

Tickets and bug reports

Support happens inside the app: a ticket with a subject and a message, attachments if you have them, and a conversation thread that shows replies. Bug reports and server reports are the same mechanism with a shorter form, so nothing gets lost between a chat message and a real ticket.

You need an account to open a ticket, because the reply has to reach you. The ticket list shows the state of everything you sent, and the conversation keeps its history.

← KodaClusterThe personal chat →
Account and support

The personal chat

Beyond tickets there is a direct line to the developer, encrypted end to end. The keys are generated on the device, the private key never leaves it, and messages are encrypted with ECDH and AES-GCM before they are stored.

On the other side only the developer can decrypt, using a key that lives in a separate admin app behind a PIN. That is the entire point of the feature: honest words stay between two people, and nobody in between can read them, including the server that stores them.

← Tickets and bug reportsThe help screen →
Account and support

The help screen

When something in a session suggests that a person is not doing well, the app shows a quiet screen that exists for one purpose: to say that someone cares and to offer real ways to get help, including hotlines, a chat service for younger people and the personal chat.

It never blocks, never reports anything, never changes a server, and disappearing from it needs a short countdown. The screen is part of the app because the people who use it are people, and the project is built by one.

← The personal chatBans and enforcement →
Account and support

Bans and enforcement

A ban is the last resort, and the app treats it that way. Server names are checked before they are created, reports are reviewed by a human, and a banned server shows a screen that explains the reason and offers a backup download instead of a dead end.

Device bans address abuse that survives reinstalls. They are rare, and the code that triggers them is deliberately narrow: file tampering with the app's own state and forged identities, nothing else.

Extensions

What extensions are

Extensions let other people add screens, languages, themes, settings rows and server tabs to the app, without forking it and without waiting for a release. A package is a ZIP file with a manifest and, usually, a small web interface. Nothing native is ever loaded, which keeps the app compatible with Play policy and keeps a broken extension from taking the app down with it.

The examples are the fastest way in, and they are all in the repository:

  • Koda Lab, the test bench that exercises every call with raw answers
  • Live Log, a screen in about a hundred lines
  • Polski, a real language pack
  • Ocean, a theme plus interface tweaks
  • The written reference, with the JSON schema beside it

← What extensions areThe bridge API →
Extensions

The bridge API

Every page your extension shows runs in a sandbox that can only reach its own files. To talk to the app it uses one global object, window.koda, injected before your scripts run. Every call returns a promise and every answer is a JSON object. Errors arrive as an object with an error field instead of an exception.

const { servers } = await koda.servers.list();
const first = servers[0];
const { lines } = await koda.console.tail(first.id, 200);

await koda.storage.set('lastServer', first.id);
const saved = await koda.storage.get('lastServer');   // { value: '...' }

const theme = await koda.theme();    // colours, so your page can match the app
const { lang } = await koda.locale();
koda.ui.toast('Hello from my pack');
const { ok } = await koda.ui.confirm('Restart?', 'Players will be kicked.');

The store and the API

The store lives at host.kodanetwork.eu/store and mirrors inside the app's extension hub under Discover. Submitting happens on the website, installing happens in the app, and both talk to the same public API.

Submitting

Sign in with the same account you use in the app, pick your .kodaext package, fill in the name, version, license and a source link, and submit. The form computes the SHA-256 of your file and the server repeats the check: it reads the manifest out of the package and refuses anything whose id, version code, license or permissions do not hold up. Nothing reaches the store before the review approves it, and the first approved version publishes the extension.

A submission is in one of five states: PENDING while it waits, APPROVED once it is live, REJECTED with a reason, DELISTED when it was taken down after the fact, and WITHDRAWN when you ended it yourself. The dashboard on the website lists your submissions with their state and the reason, so an ended extension is never a silent one.

New versions

A new version of a published extension goes through the same review. Until it is approved the store keeps serving the previous version, so a broken update can never take the published one down with it. Installing an update puts it over the existing copy and keeps its storage.

The API

Everything the website and the app do is reachable under https://api.kodanetwork.eu. The public routes need no key:

GET /v1/status                    live numbers (servers, players, store, tunnel server)
GET /v1/releases                  published app releases
GET /v1/servers                   the public server directory (name, status, players, MOTD, owner)
GET /v1/servers/{host}?ping=1     one server: owner, and a live minecraft ping (players, MOTD, favicon)
GET /v1/extensions                the catalog, approved only, with the newest version
GET /v1/extensions?author=Name    everything one publisher released
GET /v1/extensions/{id}           one extension with all approved versions
GET /v1/extensions/{id}/download  redirects to a 60 second signed url

The rest takes the Supabase session token as a bearer, the same login the dashboard uses:

GET   /v1/me                        profile, nickname, avatar url, counters, 2FA state
PATCH /v1/me                        nickname and avatar
POST  /v1/me/avatar                 upload target for a profile picture
GET   /v1/me/devices                linked devices with their telemetry and MC accounts
POST  /v1/me/devices/{id}/unlink    detach a device; the app keeps working standalone
GET   /v1/me/extensions             your submissions with their review state
GET   /v1/me/tickets                your support tickets
POST  /v1/me/tickets/{id}/messages  reply to a ticket from the browser

The server detail answers with a real minecraft server list ping when the server is reachable: live players, the MOTD and the icon the server itself advertises, all cached for a minute. The directory and the detail only ever show the owner's minecraft name, and only when that account linked one - never app uuids, tokens or hardware ids.

Two things stay out of the API on purpose. The personal support chat is end to end encrypted between the app and the admin app, so it only exists in the app. And packages are never served from a public url: a download goes through a signed link that expires after a minute, so a pending or rejected upload is not reachable by guessing paths.

Every route sits behind sliding-window rate limits (reads 120 per minute per address, writes 30, ninety per account, twenty for ticket replies and uploads), counted in the database so they hold across all edge instances. When a client hits a limit the api answers 429 with a Retry-After, and the website shows a "service is busy, please wait" screen with a countdown instead of errors.

Layout variants, and the trap that keeps biting

Central screens exist in more than one layout: a classic one, an optional Material 3 one, an optional sleek one, and for the server screen a terminal variant. The activity picks at runtime, which means a new view has to be added to every variant you actually use, or the code that looks it up has to cope with its absence.

We learned this the hard way. A settings card existed only in the classic layout, the settings screen crashed in Material 3 mode with a null pointer, and because that same screen is where the theme mode lives, there was no way back. The habit that prevents it is cheap:

View card = findViewById(R.id.card_my_feature);
if (card == null) return;      // this layout variant may not have it
card.setOnClickListener(v -> openMyFeature());

The design rules

The rules that keep the app coherent are worth stating plainly, because breaking them is visible to anyone who uses the app for a day.

  • Use the Koda palette instead of inventing greys. Orange marks actions, online marks health, red marks danger.
  • Buttons keep a 12 dp corner radius, cards a 12 dp radius on a flat surface with no shadow.
  • Every new string ships in English, German and Chinese at least, and now Polish as well.
  • Functional sheets stay functional: controls and one result, no paragraphs of prose.
  • Screens that belong to a flow copy the flow's layout instead of inventing a second look.

Infrastructure

The database

The control plane runs on Supabase, and the schema is deliberately small and readable. Everything a client is allowed to do goes through a function, tables themselves are closed to the API.

TableWhat it holds
koda_usersone row per device: app uuid, device token, linked Minecraft account, nickname, permissions, ban state
koda_serversone row per server: owner, type, version, port, join address, state, join address history
koda_portsthe port pool, with allocation and release handled by edge functions
releasesapp releases with changelog, channel, banner image and a published flag
app_settingsremote configuration: maintenance mode, minimum versions, feature flags
support_tickets, support_ticket_messagestickets and their conversation, including the encrypted personal chat
extension_*the extension registry: packages, versions, reports

Functions follow one naming rule: anything a client may call starts with rpc_, internal helpers start with fn_. Read functions that replace a table are the norm, and every write verifies the device token inside the function rather than trusting the caller.

← Adding a screen or a settingEdge functions →
Infrastructure

Edge functions

Small Deno functions handle the work that needs a secret or a decision the client should not make itself: allocating and freeing ports, checking whether a server name is free, creating and deleting DNS records, provisioning a Java runtime, and handing out the tunnel configuration after verifying a device token.

They are the only place where credentials for external services live, and each one validates its caller first. A typical request carries the app uuid and the device token, and the shared helper in supabase/functions/_shared does the verification in one place.

← The databaseInside KodaDash →
Infrastructure

Inside KodaDash

KodaDash is a Java plugin with its own small HTTP server, built on the JDK's built in server so it has no dependencies beyond the plugin API. It registers one handler per area: console, players, files, settings, plugins, logs, backups, schedule, stats, efficiency and the server actions.

The console handler is the interesting one: it attaches a Log4j appender through a dynamic proxy, keeps a bounded per client queue with a writer thread, and streams events with a line index so a reconnecting browser resumes exactly where it stopped. That is why the dashboard console survives a phone going to sleep and back.

The dashboard never writes files the app owns. The app mirrors stats, backups and the schedule into the server folder, and KodaDash reads them, which keeps one writer per piece of state.

Infrastructure

The security model

The app ships a public API key, and that is fine because the key alone authorises nothing. Every write carries the device uuid and a per device token, and the server side functions verify that pair before they touch a row.

  • Device tokens are random, per installation, and rotate when a device is reset.
  • Row level security is on everywhere, with no permissive policies on the tables clients use.
  • Admin functions additionally check an allowlist, so holding the service key is not the same as being an admin.
  • Anti tamper watches the app's own state and identity, and is deliberately narrow to avoid punishing honest users.
  • Attack simulations in the repository try the classic moves with the public key: writing without a token, escalating to admin, spoofing a ticket, reading tables directly. They must all fail.
Server side plugins have their own credentials. The KodaDash token lives in the server folder, not in the app, and a stolen token cannot delete backups by design.

Working on the code

The project uses two repositories: a private development repository and a public mirror. The mirror is produced by a script that copies tracked files, excludes the local tooling, the IDE state and database backups, and scans the result for instance data before it pushes. A pattern that has never been public before aborts the push, which is the only reason a project this size can be published safely.

Branches are simple: work happens on a feature branch, releases are tagged, and the mirror receives a snapshot commit. When you fork, the same script is your safety net for anything you adapt.

Making a release

A release is a version bump, a build, an entry in the releases table and a banner. The order matters, because the app reads the version from the database, not from the store.

  1. Raise versionCode and versionName in the Gradle file and build a signed bundle for the store and an APK for direct installs.
  2. Add a draft row to releases with the changelog, the channel and the banner, and leave it unpublished while you check it.
  3. Publish: the flag goes up, the app's update screen starts offering the new version, and the bot announces it in Discord.

Users on an older build see the update screen with the changelog text, which is why the changelog is written for people rather than for machines.

Licensing, in plain words

The project is free software under the GNU General Public License v3, and only that. Source files carry a short header that points at the license text. If you fork and publish, keep those headers and the license, and your users keep the same freedoms you got.

Third party components are listed twice on purpose: inside the app under Licenses in the settings, and on the website at host.kodanetwork.eu/licenses.html, so people can read them without installing anything. When you add a dependency, add its license text there as well.

Extensions are not covered by this license. They are separate works that run against a documented interface, and every published extension declares its own license, which the app shows to the user. That is why the license field is mandatory in the manifest and why the store recommends a source link.

← Licensing, in plain wordsQuestions that come up often →
Development

Questions that come up often

Does a server keep running when the app is closed?

Yes. The server runs in a foreground service with a notification, and the app asks for battery exceptions during setup so Android does not stop it. The console and the dashboard keep working through KodaDash while the phone sleeps.

Do I need an account?

No. An account adds the website dashboard, recovery on a new device and the family features, but hosting works without one.

Is my world uploaded anywhere?

No. Worlds stay on the device unless you start a transfer to another device, and that transfer runs directly between the two phones.

Why is the app not on the store for every country?

Because hosting needs a device with enough memory and a modern WebView, and the store listing states the requirements honestly instead of collecting refunds.

Can I host more than one server?

Yes, as long as memory allows. The app tracks the budget, and hibernation exists so inactive worlds cost nothing.

How do I get help?

Through a ticket in the app or the Discord server. The personal chat is there for things that are not about servers at all.
