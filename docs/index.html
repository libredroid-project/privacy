Documentation

Everything about running KodaHosting, extending it and making it your own. Last updated October 2026.

Getting started

KodaHosting turns a phone into a real Minecraft server. Not a client and not a remote control for somebody else's machine: the server process runs on the device, the world files sit in the device storage, and the app is the control panel around it. That one decision explains almost every design choice in this codebase, including the odd ones.

Three planes do the work, and it helps to keep them apart in your head.

  • The device plane is the app itself. It downloads server jars and Java runtimes, starts and stops the process, owns the console, browses and edits files, makes backups and applies every change. If something mutates a server, it happens here.
  • The connectivity plane is the tunnel. A bundled reverse proxy client forwards the Minecraft ports and the web dashboard through a public server, so friends can join without your home address ever leaving the router. The app fetches its tunnel credentials from the backend on demand and caches them for a few hours.
  • The control plane is Supabase. It knows who you are, which devices belong to you, which servers exist, which ports are taken, which releases are published and which extensions are approved. Every write goes through a function that checks a per device token, which is why the public key that ships inside the app cannot be abused on its own.

There is a fourth piece that surprises people. KodaDash is a Java plugin that runs inside the Minecraft server and serves a web dashboard on port 7867. The app writes small JSON files into the server folder for stats, backups and schedules, and KodaDash picks them up, which is why the dashboard still shows sensible numbers while the phone sleeps.

The parts and where they run

WhereWhat you find there

You will notice that tools/ never appears in the public repository. That is deliberate, and the next section explains why.

Where everything lives

  • github.com/libredroid-project/KodaNetwork is the public repository with the app, the dashboard plugin, SQL, examples and tools.
  • extensions/ holds the extension documentation, the JSON schema, the examples and the packaging tools.
  • Licenses lists every third party component in the browser.
  • Issues is the place for bugs, ideas and questions.

Your own instance

The public repository is a complete snapshot of the source. What it cannot contain is the instance: the addresses, keys and accounts that belong to whoever runs it. That is not a marketing trick, it is basic hygiene, and every project that hosts something for other people has to draw that line somewhere. Here is exactly where we draw it.

What is not in the public repository

Missing on purposeWhy it matters
secrets_local.hthe Supabase URL, the public key, the AI key and the tunnel host that get compiled into the app
The Supabase projectits rows, storage objects, auth users and the edge function secrets
Tunnel and DNS credentialsthe reverse proxy token and the DNS provider keys for custom domains
Signing materialthe release keystore, its passwords and the Play credentials
The admin toolsthe web panel and the Kotlin admin app, which both hold the service role key

One exception is on purpose. The imprint and the privacy policy name a real operator with a real address, because German law requires it, and a service that hides who runs it is not trustworthy anyway.

Get it running, step by step

  1. Clone the repository and build it once with JDK 21. You do not need anything else to see the app compile and start.
  2. Create a Supabase project, then apply the SQL files from supabase/ in order: the migrations first, then the security fixes, then the release and extension files. Each file ends with a statement that tells the API to reload its schema.
  3. Create the storage buckets your features need: artifacts for Java runtimes, release_images for release banners, support_attachments for tickets, extension_artifacts and extension_icons for the store.
  4. Deploy the edge functions from supabase/functions/ and give them their secrets. The app asks get-tunnel-config for its tunnel credentials, so that one you cannot skip.
  5. Run your own tunnel server, or use an existing service, and put its address together with your Supabase URL and public key into the header file that the app compiles into native code.
  6. Build a signed release and install it. The first screen registers a device and creates the row that everything else hangs off.
  7. Optional: deploy the Discord bot with your own token if you want release announcements, and the admin panel if you prefer a browser over the admin app.
A fresh instance starts empty on purpose. Without a backend the app still runs, but the first start cannot register a device and most screens stay quiet. When that happens, check the tunnel function first, because it is the only one the app truly needs.

Building the app

The project is one Gradle module plus a small native part that boots the embedded JVM, so the first build takes a few minutes and later ones are quick. Two traps cost more time than everything else combined, so they get their own paragraph.

export JAVA_HOME=/path/to/jdk-21        # newer JDKs break the Gradle version in use
./gradlew :app:assembleDebug            # debug apk
./gradlew :app:assembleRelease -PKEYSTORE_PW=... -PKEY_PW=...
adb install -r app/build/outputs/apk/release/app-release.apk
./gradlew :app:testDebugUnitTest        # unit tests, finishes in seconds

The first trap: a debug build and a release build cannot replace each other, because their signatures differ. Decide early which one your test device carries, otherwise you will uninstall the app and lose its data on the way.

The second trap: release builds strip every log call. Logcat stays completely silent in a release build, for your code and for the framework wrappers alike. Show diagnostics in the interface instead of trusting a log line, and remember that the app has its own debug log screen for exactly this reason.

The devices that matter are arm64 and run Android 11 or newer. The APK bundles only arm64 libraries, so an x86 emulator will install nothing useful. Use a real device when you want to reproduce real behaviour.

Extensions: format

Extensions let other people add screens, languages, themes, settings rows and server tabs to the app, without forking it and without waiting for a release. They are plain ZIP files with a manifest and, usually, a small web interface. Nothing native is ever loaded, which keeps the app compatible with Play policy and, just as important, keeps a broken extension from taking the app down with it.

Keep an example open next to you while you read: Koda Lab is the test bench that exercises every call, Live Log is a small screen, Polski is a real language pack and Ocean shows themes with interface tweaks.

What a package looks like

my-extension.kodaext          (a ZIP, files at the root)
  manifest.json                required
  ui/index.html                required when the extension has a screen
  ui/app.js, ui/style.css      your interface
  lang/es.json                 language packs you contribute
  automations.json             automation rules
  icon.png                     128x128, shown in the hub

Here is a manifest that uses nearly everything. Read it as a menu, then delete the parts you do not need.

{
  "schema": 1,
  "id": "eu.example.mypack",
  "name": "My Pack",
  "version": "1.0.0",
  "versionCode": 1,
  "author": "Your name",
  "description": "What it does, in one sentence.",
  "license": "GPL-3.0-or-later",
  "source_url": "https://github.com/you/mypack",
  "minAppVersion": 8514,
  "permissions": ["servers.read", "console.read", "storage", "http:discord.com"],
  "ui": { "entry": "ui/index.html", "title": "My Pack" },
  "contributes": {
    "languages": [ { "code": "es", "name": "Espanol", "file": "lang/es.json" } ],
    "themes": [ { "id": "ocean", "name": "Ocean", "color": "#006874" } ],
    "settings": [ { "title": "My Pack", "subtitle": "Open the panel", "target": "overview" } ],
    "server_tabs": [ { "id": "panel", "title": "Panel", "target": "server" } ],
    "ui": { "hide": ["btn_github_main"], "console_chips": ["/tps", "time set day"] }
  },
  "automations": "automations.json"
}
A license is mandatory. The app and the store show it, and a package without one is rejected at install time.

Extensions: the bridge

Every page your extension shows runs in a sandbox that can only reach its own files. To talk to the app it uses one global object, window.koda, which the host injects before your scripts run. Every call returns a promise and every answer is a JSON object. Errors arrive as an object with an error field instead of an exception, so a page can always show something sensible.

const { servers } = await koda.servers.list();
const first = servers[0];
const { lines } = await koda.console.tail(first.id, 200);

await koda.storage.set('lastServer', first.id);
const saved = await koda.storage.get('lastServer');   // { value: '...' }

const theme = await koda.theme();    // colours, so your page can match the app
const { lang } = await koda.locale();
koda.ui.toast('Hello from my pack');
const { ok } = await koda.ui.confirm('Restart?', 'Players will be kicked.');
CallWhat it gives you
koda.api, koda.versionthe bridge version, so you can show a friendly message on older apps
koda.servers.list(), get(id)servers with a fixed field set: id, name, type, mcVersion, state, port, address, ramMB, maxPlayers
koda.console.tail(id, lines)the last console lines, up to a thousand
koda.storage.get/set/remove/keysyour own key value store, one megabyte per extension
koda.ui.toast, koda.ui.confirmtwo small helpers that use the app's own look
koda.theme(), koda.locale()colours and language, so your page fits in

Permissions

Permissions are declared in the manifest and enforced by the app. If you did not ask for servers.read, the call comes back as an error.

PermissionState
storage, servers.read, console.readlive today
console.send, servers.controldeclared, next phase, behind in app confirmation
players.read, players.actions, files.read, notificationsdeclared, next phase
http:hostreserved for one specific web domain
The honest bit: only the read permissions are live right now. The test bench shows you exactly which answer each call gives on your build, instead of you having to guess.

Extensions: contributions

Beyond its own screen, an extension can add things to the app itself. Nothing happens quietly: every contribution is applied by the user, either through the actions sheet (long press the entry in the hub, or use the menu inside its screen) or through a normal switch.

Language packs

// lang/es.json, the keys are the app's string resource names
{
  "tab_dashboard": "Panel",
  "jars_title": "MODS Y PLUGINS",
  "sd_toast_log_copied": "Registro copiado",
  "ext_ui_chips_count": "%1$d comandos extra en la consola."
}

Packs are partial by design. Whatever you leave out stays in the language the user picked, so you can ship a small pack and grow it later. Keep placeholders such as %1$s exactly as they are in the original string, because a missing or extra one crashes the app the moment that text is formatted.

python3 extensions/tools/check_language_pack.py path/to/lang/es.json

Themes

"themes": [
  { "id": "ocean", "name": "Ocean", "color": "#006874" },
  { "id": "midnight", "name": "Midnight", "color": "#00D9FF",
    "colors": { "primary": "#00D9FF", "surface": "#07070F", "card": "#14141F",
                "text": "#EDEDF5", "text_dim": "#8C8C9C", "error": "#FF4455" } }
]

The color field alone is a seed. The app runs it through its Material 3 engine and generates a whole palette from it, which already changes buttons, cards and highlights. If you add colors, you are declaring the palette yourself: the roles primary, surface, card, text, text_dim, outline, online and error override what the engine computed, and the app derives a readable contrast colour for text on top of your accents.

Each theme gets its own switch in the actions sheet, with a small preview of its palette. Turning one on turns the previous one off, turning it off returns to the app's own colour mode.

Themes apply in Material 3 mode, which is a setting inside the app. If it is off, only the accent colour is used.

Settings entries

"settings": [
  { "title": "My Pack", "subtitle": "Everything in one screen", "target": "overview" }
]

These show up in the app's settings screen, right below the extension hub, each with a small info button that names the extension, its version, the author and the license. That button is the point: a user should never have to guess which rows come from the app and which come from a pack. Tapping the row opens your screen, and target is appended to your page address as #target so you can open the right tab of your own interface.

Server tabs

"server_tabs": [ { "id": "panel", "title": "Panel", "target": "server" } ]

This adds a tab to every server screen. Your page is loaded with the context attached, for example #server&server=the-server-id, so your interface knows which server it belongs to. That is how an extension shows something for one specific server instead of a generic list.

One honest limitation: the optional sleek layout has no shared panel container, so contributed tabs are skipped there.

Interface tweaks and automations

"ui": {
  "hide": ["btn_github_main"],
  "console_chips": ["/tps", "/list", "time set day"]
}

hide removes elements you do not want, addressed by the view ids used in the app's layouts. console_chips adds your own quick commands above the console. Both stay active while the extension is enabled, with no extra switch to hunt for.

An automations.json describes rules in the shape of trigger and actions. Triggers are server state changes, log patterns and schedules. Actions are notifications, webhooks and console commands. The format is final and validated when the package is installed, and the engine that runs the rules ships in the next phase, so think of the file today as a precise description of what your extension will do on its own.

Extensions: packaging

Two tools apply exactly the rules the app applies. An unknown view id, a missing language file, a malformed colour or a version number that does not grow will fail on your computer instead of on somebody's phone, which is the right place to find it.

# validate the manifest and build the package
python3 extensions/tools/pack_extension.py extensions/examples/koda-lab

# check a language pack before you ship it
python3 extensions/tools/check_language_pack.py my/pack/lang/es.json

To try a package, sideload it: Settings, Extensions, plus, pick the file. Updates keep the extension's storage, removing it deletes the storage with it. The hub menu has a reload entry, so you can iterate without reinstalling.

When you are happy, publish it wherever you like. The store inside the app is the curated place: a submitted package is reviewed, its license and source link are shown next to it, and it can be taken down again if it misbehaves. Before that, a GitHub release with the .kodaext attached works fine, because the app installs from any file.

Customizing the app

Translations

All interface text lives in app/src/main/res/values/strings.xml, with translations beside it in values-de, values-zh-rCN and values-pl. Android falls back to the default for anything missing, so a partial translation is genuinely useful and can grow over time.

Adding a language means creating the matching folder, adding the language to the picker in the settings activity, and nothing else. To keep translations honest the repository ships a checker that catches the two mistakes that actually hurt, keys that do not exist and placeholders that drifted.

python3 extensions/tools/check_translation.py app/src/main/res/values-pl/strings.xml
Run it after every batch of translations. A broken placeholder does not look wrong, it crashes at runtime the moment the string is used.

Theming in code

The app is Material 2 at heart with an opt in Material 3 mode that generates a full colour scheme from a seed. In Material 3 mode the helper resolves the colour roles once and styles whole view trees with them, which is also where extensions hook in. The palettes live in colors_m3.xml with the night variant beside it. If you want a colour decision that applies everywhere, that helper is the single place to change it.

Layouts, and the trap that keeps biting

Central screens exist in more than one layout: a classic one, an optional Material 3 one, an optional sleek one, and for the server screen a terminal variant. The activity picks at runtime. That means a new view has to be added to every variant you actually use, or the code that looks it up has to cope with its absence.

We learned this the hard way. A settings card existed only in the classic layout, the settings screen crashed in Material 3 mode with a null pointer, and because that same screen is where the theme mode lives, there was no way back. The habit that prevents it is cheap:

View card = findViewById(R.id.card_my_feature);
if (card == null) return;      // this layout variant may not have it
card.setOnClickListener(v -> openMyFeature());

Branding and the design rules

Icons, the K monogram and the brand colours live in branding/ and are generated by a script, so you change the source instead of twenty files. Fonts are referenced as font_koda for the interface and font_koda_mono for logs and code, and their licenses sit next to all the others in the licenses folder.

The rules that keep the app coherent are worth stating plainly, because breaking them is visible: use the Koda palette instead of inventing greys, keep buttons at a 12 dp corner radius, ship every new string in English, German and Chinese at least, and keep functional sheets functional, which means controls and no prose.

Licensing

The project is free software under the GNU General Public License v3, and only that. Source files carry a short header that points at the license text. If you fork and publish, keep those headers and the license, and your users keep the same freedoms you got.

Third party components are listed twice on purpose: inside the app under Licenses in the settings, and on the website at host.kodanetwork.eu/licenses.html, so people can read them without installing anything. When you add a dependency, add its license text there as well, next to the others.

Extensions are not covered by this license. They are separate works that run against a documented interface, and every published extension declares its own license, which the app shows to the user. That is why the license field is mandatory in the manifest and why the store recommends a source link: installing somebody else's code should never be a blind decision.
